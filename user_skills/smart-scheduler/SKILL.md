# 智能约会 (Smart Scheduler) V2.9

version: 2.9
updated_at: 2026-06-30

本技能致力于通过“先盘后建”的策略，高效、智能地完成团队会议安排。V2.8.1 在 V2.8 的基础上新增了**通知 payload 零信任补丁**：凡进入 Stage 3 的通知卡片 / post payload，必须先落盘到 `/workspace/.ephemeral_pool/`，文件名强制包含当前 `task_id`，严禁再使用根目录 `card.json` / `post.json` / `payload.json` 等静态文件名；调用 `feishu-im-send` 时必须显式传入 `--task-id` 与 `--topic`，让底层在发送前执行路径校验与主题一致性断言，若 payload 与当前主任务意图不一致则立即熔断。V2.8 则进一步把确认链路从“有人类能读懂”升级为“机器也能断言”：`render_confirmation_prompt.py` 现在会为候选矩阵输出结构化 Markdown 表格，并附带可程序消费的 `routing_contract`（含 `route / allow_thread_reply / reason / user_action`），把“确认默认必须走 L0 新消息”从说明层下沉为可执行契约；V2.7 新增“确认话术路由补丁”与标准确认文案脚本，明确候选矩阵/抢占确认默认走 **L0_FLAT 新消息**，避免确认环节被误导回 Thread；V2.6 引入了“时区实拿 SOP”绝对红线，封堵靠姓名盲推时区的幻觉；V2.5 引入了动态标题模板及运行时强校验机制；V2.3 在 V2.2 的基础上，进一步将默认 Sync 标题规范、10:00-19:00工作基准和跨国修仙降级策略（19:00-次日01:00）强制锁定为三大系统红线，确保“规则说明 = 默认行为”；同时保留 V2.0 的**抢占模式**、**候选矩阵**、**批量创建**与**免会议室流**等能力，在保障确定性的同时，进一步提升跨时区约会的可用性与一致性。

## 🔑 触发词

- 核心关键词：
  - 找空闲时间
  - 排期 / 约会 / 约会议
  - `约会` / `/约`（命中即强制路由到本技能）
  - 忙闲矩阵
  - 抢占 Tentative 档期
  - 批量创建会议
- 典型指令示例：
  > 帮我找奇楠和 London 同学下周的 30 分钟空档
  > 生成一个忙闲矩阵，我选完后你再建会
  > 没有绝对空闲的话，看看能不能抢占 Tentative 档期

## 【绝对红线-0】先给候选再确认（禁止直接建会）

- **必须先给“黄金候选”再等用户 pick**：无论找到多完美的交集，都必须先输出 **2-3 个黄金候选时段**（优先下午，如 14:00+），并 **显式等待用户选择**。
- **“显式确认”判定标准**：必须收到用户明确 pick（例如“选第 2 个 / 就 15:00 / 确认 4 月 29 日 14:30”），否则一律视为 *未确认*。
- **严禁一步到位越权**：任何情况下都不得在未收到 pick 前调用任何“日历写入/创建/邀约”能力（包括但不限于 `batch_create_events.py` 的下游创建动作）。

## Anti-rationalization（反找借口）护栏

### Common Rationalizations（常见 AI 借口，看到就要警惕）
- “用户没说要确认，所以我直接帮他订了。”
- “时间很紧，我就省略确认一步，先把会发出去再说。”
- “对方是高级岗/外部同学，得赶紧锁时间，不然就没了。”

### Red Flags（危险信号，一旦出现立即熔断回到确认态）
- 在**同一次**工具调用/同一段动作里，既做忙闲盘点，又直接创建/发送邀约。
- 输出里没有出现“候选时段清单 + 请用户选一个”的明确交互语句。
- 进入创建前，没有任何“用户已 pick”的可追溯证据。

### Verification（创建前必过 Checklist，不满足任一条就停）
- [ ] 已输出 **2-3 个黄金候选时段**（优先下午），并收到用户**显式 pick**
- [ ] 待创建时段默认避开饭点 `12:00-14:00`、`18:00-20:00`（除非用户明确要求占用饭点）
- [ ] 待创建日程标题最终必须以 `【预占】` 开头（否则熔断）
- [ ] 默认免会议室流（`room_mode=skip`）；若要预定会议室，已收到用户明确要求（否则熔断）

## Title 规范（绝对红线）

创建日程的标题必须遵守以下规范，并在运行时受强制校验：

1. **必须以 `【预占】` 开头**：任何日程的标题前缀必须为 `【预占】`。
2. **单对单会议（2人）**：
   - 默认模板：`【预占】<对方> × 奇楠`
   - 不得随意篡改格式。
3. **多人会议（3人及以上）**：
   - 必须向用户询问会议主题。
   - 默认模板：`【预占】<主题> (多人，需询问)`（仅作说明，实际创建必须包含具体主题）。
   - 如果用户没有给出主题，必须拒绝创建并提示用户补充主题，严禁只发 `【预占】` 或者 `【预占】多人会议` 等空泛标题。

## 核心红线：严禁自动预定

- **先盘后建，严禁越权**：在用户明确给出具体的时间段之前，本技能无论如何**只能处于排查与查询模式**。即使找到了可用的时间交集，也必须先将推荐的 2-3 个时段输出给用户，等待用户的显式确认。
- **时段偏好策略**：推荐时段应**优先选择下午时段**（如 14:00 以后），**尽量避免大清早**（如 09:00）的时段，除非用户有明确指示或下午已无任何空档。
- **接口调用限制**：绝对禁止未经用户显式确认（如“选第2个”、“确认预定xx点”）擅自调用任何日历写入/预定接口（如 `batch_create_events.py`）！

## 【绝对红线】默认工作时间窗口（跨时区）

在用户未显式给出“某天的具体时间段”时（例如只说“下周找半小时 sync”），必须使用以下默认窗口生成候选查询区间（用于 Stage 1 的 `candidate_windows`）：

1. **默认工作时间段（双方各自时区）**：`10:00-19:00`（替代旧版 `09:00-18:00`）。
2. **优先策略（求交集）**：将双方各自工作时间转换到统一时间线后，取交集作为可选窗口。
3. **跨时区降级窗口（单向延长，仅奇楠）**：若双方 `10:00-19:00` 的交集为空，则仅将用户（奇楠）的可选窗口单向延长为 **`19:00-次日 01:00`（用户时区）**，并在该窗口内再次与对方 `10:00-19:00` 求交集。

实现约束：
- 默认窗口生成逻辑已固化在 `scripts/suggest_timeslots.py` 的 `build_default_candidate_windows(...)` 中；除非用户显式指定时间段，否则上层必须使用该方法生成 `candidate_windows`。

## 【绝对红线】默认日程标题

除非用户显式指定标题（或在创建参数中提供 `base_title`），创建日程的默认标题必须严格遵循 **Title 规范**。

实现约束：
- `scripts/batch_create_events.py` 的 `validate_title` 和 `build_default_title` 在 `base_title` 为空时，会根据参会人数进行动态模板应用和强制校验。

## 【绝对红线-5】对方时区：必须实拿，不许实猜

约会涉及跨时区时，对方时区的确定必须走"实调 API"三级路径，禁止靠姓名/会议时段等弱信号盲推。

### 时区获取 SOP（从 L1 到 L3 依次尝试，严禁跳过）

| 级别 | 来源 | 字段 | 强制性 |
|---|---|---|---|
| L1 | 飞书 Contact API `/open-apis/contact/v3/users/{user_id}` | `time_zone` | 必调 |
| L2 | 飞书 Calendar API `/open-apis/calendar/v4/calendars/primary` | `time_zone` | L1 空/拿不到时必调 |
| L3 | 对方近 2 周日程事件 `start_time.timezone` 众数 | — | L1/L2 都空时作为旁证 |

### 禁用信号（永远不能单独作为时区依据）

- ❌ 姓名拼写风格（如 Haersh Sahita → 盲推印度）
- ❌ 会议集中时段倒推（如 BJT 21:30 结束 → 盲推 IST 19:00 下班）
- ❌ 邮箱后缀 / 工位座位号 / 直觉

### 拿不到怎么办

L1/L2/L3 全部空，必须显式汇报"**对方时区未能权威获取**"并列出已尝试来源，交由用户裁决，**严禁自己拍板**。

## SOP 流程 V2.0：盘、决、建

为实现更灵活、更智能的调度，V2.0 将原有的“查-锁-建”升级为“盘、决、建”三阶段：

### Stage 1：查询与盘点 (Check & Inventory)

1.  **绝对空闲优先**: 首先，调用 `scripts/suggest_timeslots.py` 的 `classify_timeslots` 方法，在候选时间窗口内寻找所有参与者均**绝对空闲**的时段。
2.  **兜底抢占扩展**:
    - 若找不到绝对空闲时段，且 `preemption_enabled` 为 `true`，则启动抢占模式。
    - 此时，`classify_timeslots` 会进一步识别那些仅与“未接受 (Tentative)”日程冲突的**可抢占候选**时段。
    - 每个抢占候选会附带被占用人、事件标题及冲突权重等信息，供后续决策。

### Stage 2：候选矩阵与决策 (Candidate Matrix & Decision)

1.  **生成候选矩阵**:
    - 将 Stage 1 产出的“绝对空闲”与“可抢占”时段整合为候选列表。
    - 调用 `scripts/build_availability_xlsx.py` 生成一个可视化的忙闲矩阵 `.xlsx` 文件。该矩阵支持多天展示，并用不同颜色标注各时段的参会人覆盖率，直观反映优劣。
    - **禁止自动发送邀请**: 此阶段严禁直接创建任何日历事件。
2.  **决策权交付**:
    - 将生成的 `.xlsx` 文件上传并转换为飞书在线表格。
    - 向用户提供表格链接，并默认推荐三组最优选项（例如，综合考虑覆盖率与冲突权重）。
    - 若需生成标准确认话术，优先执行 `python3 scripts/render_confirmation_prompt.py --mode matrix ...`，输出带 routing contract 的确认文案。
    - 附上明确的用户话术（参考下文模板），等待用户做出显式选择（如“选第2个”、“确认抢占14:00的会”）。
    - **Stage 2 停车锁（新增强制红线）**：一旦候选矩阵 / 2-3 个黄金候选已输出，必须立刻设置 `explicit_user_pick=pending` 并停止流程；在该状态解除前，流程只能继续等待用户 pick，禁止任何形式的自动推进。

### Stage 3：正式创建与通知 (Create & Notify)

> **Stage 3 准入前提（新增强制断言）**：只有 `explicit_user_pick=confirmed` 且存在用户明确选定的可追溯证据时，才允许进入本阶段；若仍为 `pending`，必须直接熔断并返回确认态，禁止调用任何日历写入工具。

**Stage 3 三件套门禁（RE-20260630-001 补丁）**：进入任何日历写入入口前，必须同时满足以下 3 个机器可断言字段；缺任一项即立刻熔断，禁止建会，并回到 Stage 2 确认态：
- `explicit_user_pick=true`：必须是布尔真值；`pending`、`confirmed` 文本、空值或缺失均不合格。
- `selected_slot` 非空：必须包含用户选定的具体候选时段或候选 ID，不能只写“已确认”。
- `pick_evidence` 非空：必须保存用户原话证据，例如“选第 2 个”“就 15:00”“确认 7 月 2 日 14:30”。

**路由独占规则（禁止裸建会）**：命中 smart-scheduler 后，流程只能通过本技能的先盘后建状态机推进；禁止绕过本技能裸走 `feishu-calendar create` / `calendar +create` 或任何等价日历创建入口。在 `explicit_user_pick=true`、`selected_slot` 非空、`pick_evidence` 非空三件套齐备前，仅允许执行 freebusy / suggestion / 候选输出类查询与推荐动作。

1.  **批量或单次创建**:
    - **批量场景**: 若用户选择了多个时段，调用 `scripts/batch_create_events.py`。该脚本会接收包含多个时段的 JSON 配置，并为整批操作生成**一个统一的幂等性 Key** (`idempotency_key`)。
    - **单次场景**: 沿用原有逻辑，使用 `scripts/generate_idempotency_key.py` 生成单个 Key。
2.  **应用动态配置**:
    - **标题前缀**: 若 `title_prefix` 参数非空（如 `【预占】`），则统一添加到所有待创建的日程标题前。
    - **免会议室流**: 根据 `room_mode` 参数 ('auto' 或 'skip') 及参会人数，决定是否跳过会议室搜索环节。
3.  **执行与通知**:
    - 携带幂等 Key，调用飞书日历 API 创建日程。
    - 向相关群组或人员发送极简通知（日程卡片链接），**严禁**附带视频会议链接。
    - **通知 payload 物理隔离（新增硬规则）**：所有通知卡片 / post payload 必须先落盘到 `/workspace/.ephemeral_pool/`，并使用 `[TASK_ID]_[TOPIC_SLUG].card.json`、`[TASK_ID]_[TOPIC_SLUG].post.json` 等唯一文件名；严禁写入根目录 `card.json` / `post.json` / `payload.json`。
    - **发送前主题断言（新增硬规则）**：调用 `feishu-im-send` 时必须传入 `--task-id` 与 `--topic`，由底层比对 payload 标题/摘要与当前主任务意图是否一致；若检测到旧主题或缺少上下文，必须立即熔断，不得带病发送。

## 参数开关与默认值

| 参数 | 描述 | 默认值 |
| --- | --- | --- |
| `preemption_enabled` | 是否启用抢占模式。`true` 时，在无绝对空闲时段后，会自动查找可抢占的 Tentative 日程。 | `true` |
| `preemption_sensitivity` | 抢占敏感度，一个 `0.0` 到 `1.0` 的浮点数。控制可被 Tentative 事件影响的参会人占比阈值。例如，`0.5` 表示最多一半参会人有 Tentative 冲突时，该时段才可被视为候选。 | `1.0` |
| `title_prefix` | 动态标题模板描述。需根据“Title规范”填充对应的模板，详见下方说明。 | `【预占】<对方> × 奇楠 (单对单) / 【预占】<主题> (多人，需询问)` |
| `room_mode` | 会议室预定模式。`'skip'` 表示强制跳过会议室搜索；`'auto'` 表示当参会人数 ≤ 2 或明确指定为线上会议时自动跳过，否则按默认策略查找（如“尚浦中心6楼”）。 | `'skip'` |
| `default_duration` | 默认会议时长（分钟）。V2.0 支持在调用时传入自定义时长（如 `90` 分钟）。 | `30` |

*说明：`title_prefix` 在 V2.5 及以上版本不再是简单的固定字符串，而是代表遵守 Title 规范。在实际执行时，脚本会根据参会人数（2 人还是多人）自动推导或强制校验具体的日程标题。*

### 默认窗口生成参数（仅在用户未指定具体时间段时生效）

> 上层在构造 Stage 1 的 `candidate_windows` 时，优先调用 `scripts/suggest_timeslots.py` 的 `build_default_candidate_windows(...)`，并遵循下表默认值。

| 参数 | 描述 | 默认值 |
| --- | --- | --- |
| `user_tz` | 用户（奇楠）时区（IANA tz name）。 | `Asia/Shanghai` |
| `counterpart_tz` | 对方时区（IANA tz name）。 | `Asia/Shanghai`（若未知需显式提供） |
| `work_start_hour` | 双方各自时区的工作日开始小时（24h）。 | `10` |
| `work_end_hour` | 双方各自时区的工作日结束小时（24h）。 | `19` |
| `fallback_user_start_hour` | 跨时区降级窗口：用户晚间窗口开始小时（24h）。 | `19` |
| `fallback_user_end_hour_next_day` | 跨时区降级窗口：用户晚间窗口结束小时（次日，24h）。 | `1` |

### 候选矩阵与决策确认

> "根据您的要求，我为您筛选了以下几个备选时段，并生成了详细的忙闲矩阵供您决策：
>
> **推荐方案（双时区并列显示）：**
> 1.  **周二 15:00-15:30 BJT / 08:00-08:30 BST** (覆盖率 100%)
> 2.  **周二 16:00-16:30 BJT / 09:00-09:30 BST** (覆盖率 100%)
> 3.  ⚠️ **周二 22:00-22:30 BJT / 15:00-15:30 BST** (覆盖率 100%，但 BJT 已超 20:00，属"跨国修仙"时段，请确认可接受)

**双时区显示与盲区警示规则**：
- 候选时段必须强制显示 `我方 BJT / 对方本地时区` 双标
- 以对方 10:00-19:00 当地时为默认池（V2.3 已定）
- 换算到我方 BJT 若落在 `< 08:00` 或 `> 20:00`，必须在候选前加 ⚠️ 标红提示"跨国修仙"时段，**但保留候选不静默剔除**，由用户决策
>
> 👉 **[点击查看完整忙闲矩阵](https://bytedance.larkoffice.com/sheets/shtcnxxxx)**
>
> 请直接发送一条**新消息**告知您选择的方案序号（如“1”），或说明最终决定；不要隐式继承当前 Thread / 话题楼层。确认后我再继续创建这些会议。"

**消息路由补充约束**：
- 候选矩阵、忙闲分析、确认提示默认均走 **L0_FLAT 新消息**。
- 禁止助手为了“上下文连续”擅自使用 `reply_to`、Thread 盖楼或话题继承。
- 只有命中 `route_manifest.yaml` 白名单的场景，才允许 L1 话题回复。
