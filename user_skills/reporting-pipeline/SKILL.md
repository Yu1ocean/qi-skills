# Reporting Pipeline

## Common Rationalizations（常见借口）

以下想法出现时，立即回到本 SOP：

- “先把素材整理成稿子，评分和对比以后再补。”
- “原始记录太散，可以直接按经验补一版漂亮汇报。”
- “三个子技能都差不多是写作，不需要明确分阶段。”
- “飞书归档只是最后贴链接，不需要 RAW 回捞或权限检查。”
- “缺少目标、时间窗或数据锚点时，先假设一个合理口径。”

## Red Flags（危险信号）

出现任意一条，必须先纠偏再继续：

- 没有区分 S1 素材召回、S2 升维改写、S3 打分对比，直接输出单版稿。
- 最终稿只有语言润色，没有管理判断、责任链、数字锚点或资源动作目标绑定。
- 子技能依赖关系写成脚本直连、内部路径直调或跨技能 API 穿透。
- 用户提供飞书链接但没有先读取/提炼其内容就进入写作。
- 归档到飞书文档时没有使用 `feishu-doc-writing-guide`，或没有确认文档直达链接。
- 缺数据时出现虚构数字、过度归因或把团队成果直接写成个人贡献。

## Verification（强制验收清单）

宣称完成流水线时，必须同时满足：

1. **S1 完成**：使用 `performance-review-writer` 完成素材召回、候选重点工作归组、OKR/目标对齐、影响力证据与缺口标注。
2. **S2 完成**：使用 `upward-reporting-escalator` 将素材稿升级为判断稿与决策稿，并说明升级点。
3. **S3 完成**：使用 `upward-reporting-coach` 对关键版本做 10 分制评分，输出逐条扣分原因、前后对比和最终改写建议。
4. **飞书归档完成**：使用 `feishu-doc-writing-guide` 创建或更新飞书文档，默认落个人空间，并返回文档直达链接。
5. **缺口显影**：缺少目标、时间窗、角色边界、数据锚点或资源诉求时，必须写入“待确认”，不得编造。
6. **可提交性**：最终稿必须能直接复制到汇报、绩效系统、周报/月报或管理层材料中。

## 📌 技能简介

本技能是中文职场汇报的端到端编排层。它不替代三个子技能，而是规定它们的先后关系、交接字段和最终验收标准：先把散乱工作记录蒸馏成可信素材，再把执行语言升级成管理层能判断的决策稿，最后用评分与对比版本完成质检，并归档到飞书文档。

适用对象包括绩效自评、老板过稿、项目阶段汇报、周报/月报升维、晋升材料草稿和跨团队重点项目总结。

## 输入协议

接受以下输入形态：

- 原始工作记录文本、周报、会议纪要、项目复盘、OKR/目标描述。
- 飞书文档、飞书表格、Wiki、Minutes 或其他可读链接。
- 可选补充：受众、提交场景、时间周期、目标档位、重点项目、必须保留或删除的信息。

若用户只给链接，先读取链接内容再进入 S1。若链接无法读取，输出卡点和待用户处理项；不要基于链接标题猜内容。

## 输出协议

默认输出一份飞书文档，正文包含以下模块：

1. **一页纸最终汇报稿**：可直接提交的版本。
2. **S1 素材召回摘要**：重点工作、角色、结果、来源、缺口。
3. **S2 升维过程**：执行稿 → 判断稿 → 决策稿的关键跃迁。
4. **S3 评分与对比**：10 分制评分、扣分项、改写前后差异。
5. **待确认清单**：缺少的数据、目标、时间窗、资源诉求或角色边界。
6. **来源索引**：用户提供的文档、文字或链接来源。

聊天窗口只返回不超过 3 行摘要和飞书文档直达链接。

## ⚙️ 核心架构 / SOP / 约束条件

### S0. 输入预检与任务定界

先识别汇报场景：绩效自评、老板汇报、项目复盘、周报月报、晋升材料或通用管理层同步。记录受众、时间周期、目标、素材来源和硬性约束。

正式处理前，可运行 `python3 scripts/validate_pipeline_payload.py <payload.json>` 校验输入结构。校验失败时只输出缺口清单，不进入虚构写作。

### S1. 素材召回：使用 `performance-review-writer`

使用 `performance-review-writer` 完成素材召回与证据归组。交付给下一阶段的字段至少包括：事项、用户角色、结果/影响、来源、OKR/目标锚点、证据状态、待补缺口。

此阶段的成功标准不是“素材越多越好”，而是把零散记录收敛为 2-5 条能支撑校准的重点工作，并克制归因。

### S2. 升维改写：使用 `upward-reporting-escalator`

使用 `upward-reporting-escalator` 把 S1 的重点工作稿升级为判断稿和决策稿。必须完成三类跃迁：把“做了什么”改为“现在怎么看”，把零散动作收束成责任链，把关键数字绑定到时间窗、目标或资源动作。

若目标、时间窗或资源诉求不足，保留“待确认”占位，禁止脑补。

### S3. 打分与版本对比：使用 `upward-reporting-coach`

使用 `upward-reporting-coach` 对 S2 版本进行 10 分制评分，至少覆盖判断先行、分工清晰、数字有锚、结构分层和诊断语气五项。输出最终稿前，必须说明扣分项如何被修正，并保留前后版本差异摘要。

### S4. 飞书归档：使用 `feishu-doc-writing-guide`

最终结果必须归档到飞书文档。创建新文档时默认使用个人空间优先策略；更新已有文档时先读取目标内容再写入。归档后返回文档直达链接，并在必要场景执行写后回读或结构检查。

文档标题建议格式：`汇报稿｜<主题>｜<YYYY-MM-DD>`。

## 文档生动化标准

当本技能产出正式汇报文档时，应把文档头部做成“管理层先读区”：先放最终结论、提交版正文和评分结果，再放过程稿。若任务同时要求复盘、归档或庆祝卡片，可使用 `cyber-inspiration-generator` 生成视觉摘要并前置嵌入，但不得因此延迟核心汇报稿交付。

## 合规默认值（Defaults）

- 默认语言：简体中文。
- 默认输出容器：飞书文档。
- 默认受众：管理层 / 直属上级。
- 默认阶段：完整执行 S1 → S2 → S3 → S4。
- 默认重点工作数量：2-5 条，优先 3 条。
- 默认缺口处理：写“待确认”，不编造。
- 默认归档方式：通过 `feishu-doc-writing-guide` 创建或更新文档。

## 运行时断言

在进入飞书归档或正式输出前，检查：

- 是否已有 S1 结构化素材表。
- 是否已有 S2 判断稿与决策稿。
- 是否已有 S3 评分结果与修正说明。
- 是否标明所有待确认字段。
- 是否准备通过 `feishu-doc-writing-guide` 完成飞书文档创建/更新。

任一缺失时，先补齐缺口；无法补齐则在最终文档中显影，不得静默跳过。

## 📖 案例实录 (Best Practice)

- 🧑‍💻 用户输入：
  ```text
  这些是我 Q3 的工作记录和几篇项目复盘链接，帮我生成一份可以给老板看的汇报稿，并归档飞书。
  ```
- 🤖 标准输出：
  ```text
  已按 S1→S2→S3→S4 完成：先将原始记录收敛为 3 条重点工作，再升级为判断稿和决策稿，随后按 10 分制完成评分与改写，最终归档到飞书文档。聊天窗口只返回文档链接、Skill ID 和 RAW 入库信息。
  ```

## 质量边界

- 不虚构业务数字、组织影响、职级贡献或协同方。
- 不把团队成果直接写成个人贡献。
- 不绕过三个子技能直接生成单版润色稿。
- 不用裸调 lark 工具替代 `feishu-doc-writing-guide` 完成归档。
- 不把飞书文档链接当作已读内容；必须先读取或标注读取失败。
