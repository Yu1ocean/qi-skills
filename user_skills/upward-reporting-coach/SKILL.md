# Upward Reporting Coach

## Common Rationalizations（常见借口）

以下说法一旦出现，视为开始偏离技能目标，必须立刻切回本 SOP：

- “大意差不多，就不给逐条打分了。”
- “直接帮他润色一下，不用解释为什么扣分。”
- “范文看着不错，没必要抽象成规律。”
- “规范文档只是参考，不需要和现有规律库比对。”
- “有点像新增规律，但先放过，不归档也没关系。”
- “冲突点不明显，先默认都成立。”

## Red Flags（危险信号）

出现任意一条，必须纠偏后再继续输出：

- 评分维度不是基于当前规律库，而是临时换了一套标准。
- 总分不是 10 分制，或每条规则不是 0-2 分。
- 只给总评，不给单条得分理由。
- 给了改写建议，但没有给出完整改写段落。
- 规律迭代时没有区分“新增 / 强化 / 冲突”。
- 从规范文档提炼规则时，没有与现有规律库逐条对比。
- 把表达偏好误判为普适规律，没有说明适用边界。

## Verification（强制验收清单）

当输出完成时，必须同时满足：

1. **场景识别正确**：明确当前属于“打分改写 / 分析迭代 / 规范文档提炼”三类中的哪一类。
2. **规则基准一致**：默认使用当前规律库作为唯一评分与分析基准。
3. **评分完整**：场景 1 必须逐条给出 5 条规律的 0-2 分评分、扣分原因、总分。
4. **改写闭环**：场景 1 必须给出可直接复制使用的完整改写段落。
5. **分析闭环**：场景 2 必须说明“哪些表达被升级了、为什么更适合向上汇报、是否产出新规律”。
6. **规范抽取闭环**：场景 3 必须输出“新增 / 强化 / 冲突”三类结果，并更新规律库视图。
7. **边界清晰**：若输入不足以支持强判断，必须明确标注“待确认”而不是强行下结论。

## 📌 技能简介

这个技能用于把“好的向上汇报”从感觉题，压缩成一套可重复执行的判断框架。它聚焦中文职场与管理层汇报场景，不只做语言润色，更强调：**先判断，再改写；先抽规律，再沉淀复用。**

默认输出语言为简体中文，语气要求专业、结构化、可直接落地。

## 🔑 触发词

- 核心关键词：
  - 向上汇报
  - 管理层汇报
  - 老板视角改写
  - 汇报打分
  - 汇报规律
  - 汇报模板提炼
- 典型指令示例：
  > 给这段汇报文字按向上汇报规律打分，并直接帮我改写
  > 对比这两版汇报文案，提炼更适合向上汇报的表达规律
  > 从这份汇报规范里抽取规律，并和现有规律库比对

## 适用场景

### 场景 1：打分 + 改写建议

**输入：** 1 段汇报文字。

**输出：**
- 按 5 条规律逐条打分（每条 0-2 分，满分 10 分）
- 每条给出得分理由
- 汇总主要短板
- 输出一版完整改写段落

### 场景 2：分析 + 迭代规律

**输入：**
- 2 段前后改写文字；或
- 1 段范文

**输出：**
- 对比两版差异，或提炼范文亮点
- 识别哪些表达更符合向上汇报逻辑
- 判断是否形成“新增规律 / 旧规律强化 / 仅案例，不升格为规律”
- 若可升格，更新规律库

### 场景 3：规范文档迭代规律

**输入：** 1 份规范文档，如公司汇报模板、写作指南、老板偏好说明。

**输出：**
- 从文档中提炼候选规律
- 与现有规律库逐条比对
- 归类为：**新增 / 强化 / 冲突**
- 输出更新后的规律库视图

## 当前规律库（初始版本）

详细内容见 `references/rule-library.md`。默认以该文件中的“active”规则为单一事实来源。

当前 5 条基础规律：

1. **判断先行，不是进度汇报** —— 先给结论，再说动作。
2. **分工描述是管理信号** —— 让领导确认责任是否到位、资源是否覆盖。
3. **数字要有锚** —— 公式：变化 + 时间节点 + 支撑目标。
4. **三层比五条清单更清晰** —— 分层体现先后顺序和优先级。
5. **诊断语气建立信任** —— 给出自己的诊断再说解法，动作是结论的附属物。

## 输出协议

### 场景 1 输出格式

按以下结构输出：

1. **总评**：一句话概括当前这段话更像“执行汇报”还是“决策汇报”。
2. **逐条打分**：
   - 规律 1：X/2 —— 理由
   - 规律 2：X/2 —— 理由
   - 规律 3：X/2 —— 理由
   - 规律 4：X/2 —— 理由
   - 规律 5：X/2 —— 理由
3. **总分**：X/10
4. **改写建议**：列出 2-4 条最关键修改动作
5. **改写后完整段落**：给出可直接复制的最终版本

### 场景 2 输出格式

按以下结构输出：

1. **差异总览**：一句话说明升级方向
2. **核心变化**：从“结论前置 / 分工清晰 / 数字锚点 / 结构层次 / 诊断语气”中逐条分析
3. **规律判断**：
   - 继承旧规律
   - 强化旧规律
   - 候选新增规律
4. **规律库更新建议**：
   - 若不升级为规律，说明原因
   - 若升级，给出新增规则名称、定义、适用边界、示例

### 场景 3 输出格式

按以下结构输出：

1. **文档核心导向**：该规范最强调什么
2. **候选规律提炼**：从文档抽出的规则清单
3. **与现有规律库对比**：分为“新增 / 强化 / 冲突”三栏
4. **冲突处理建议**：若发生冲突，说明是“替换 / 并存 / 待确认”
5. **更新后规律库视图**：输出当前推荐版本

## 规律库迭代规则

### 何时允许升格为新规律

候选表达只有在同时满足以下条件时，才允许升格为规律：

1. **跨样本稳定**：不是只对单一案例成立。
2. **具有判断力**：能帮助区分“普通汇报”与“好的向上汇报”。
3. **可操作**：可以转化为明确的写作动作。
4. **不与现有规则重复**：若只是已有规则的另一种说法，归入“强化”而非“新增”。

### 新规律推荐写法

新增规律统一写成以下四段：

- **规律名**：一句短标题
- **定义**：这条规律在判断什么
- **适用边界**：什么场景适用，什么场景不必强求
- **示例**：给一条正例，必要时给一条反例

## 工作流 / SOP

### Step 1. 识别输入类型

先判断输入属于哪类：
- 单段文字 → 场景 1
- 两版文字或范文 → 场景 2
- 规范/模板/指南文档 → 场景 3

若用户提供的信息混合，优先以其最核心目标为准；必要时先声明“本次按场景 X 处理”。

### Step 2. 读取规律库

先读取 `references/rule-library.md`，确认当前 active 规则、已有新增规则、历史冲突记录。

### Step 3. 执行对应分析

- **场景 1**：先判断原文最核心缺口，再逐条打分，最后统一改写。
- **场景 2**：先看“升级了什么”，再判断“为什么升级有效”，最后决定是否沉淀为规律。
- **场景 3**：先抽规则，再做映射，不要直接把规范原文逐句复述成结论。

### Step 4. 输出结构化结果

输出要能兼顾两层读者：
- **作者自己**：知道该怎么改
- **管理者 / 复盘者**：知道这段话为什么更适合向上汇报

### Step 5. 更新规律库视图

若本轮分析产生可升格规律，按以下方式更新：

1. 在结果中给出新增或强化说明；
2. 更新 `references/rule-library.md` 的 active 或 proposed 区域；
3. 若证据不足，则写入候选而不是强行激活。

## 判断标准细化

### 规律 1：判断先行，不是进度汇报
- **2 分**：开头直接回答“现在怎么看 / 为什么重要 / 建议怎么定”。
- **1 分**：有结论，但藏在中后段。
- **0 分**：只罗列动作、过程、状态。

### 规律 2：分工描述是管理信号
- **2 分**：责任主体、协同对象、资源覆盖都清楚。
- **1 分**：提到分工，但领导看不出谁负责什么。
- **0 分**：完全没有角色与责任视角。

### 规律 3：数字要有锚
- **2 分**：数字同时带变化、时间点、业务目标。
- **1 分**：只有数字，没有时间或目标锚点。
- **0 分**：数字空泛，或完全没有可验证信息。

### 规律 4：三层比五条清单更清晰
- **2 分**：存在清楚层次，能看出优先级与顺序。
- **1 分**：有分点，但层次混杂。
- **0 分**：平铺罗列，重点不突出。

### 规律 5：诊断语气建立信任
- **2 分**：先判断问题本质，再给动作建议。
- **1 分**：有诊断意识，但解法先于判断。
- **0 分**：只有动作，没有诊断。

## 合规默认值（Defaults）

- 默认语言：简体中文
- 默认对象：中文职场中的向上汇报 / 管理层汇报
- 默认评分尺度：每条 0-2 分，总分 10 分
- 默认规则来源：`references/rule-library.md` 中的 active 规则
- 默认新增规则状态：`proposed`，需有明确证据后再转 `active`
- 默认冲突处理：先保留冲突说明，不擅自删除旧规则

## 脚本与运行时断言

使用 `scripts/validate_rule_update.py` 对候选规律更新进行前置校验，确保：
- 输入场景合法
- 规则状态合法
- 新规律字段完整
- 冲突分类合法

若校验失败，必须停止更新，并明确报错原因。

## ⚙️ 核心架构 / SOP / 约束条件

- 本技能的核心不是“改得更顺”，而是“更像管理层需要的信息结构”。
- 不把辞藻华丽当成好汇报。优先判断、结构、数字锚点与诊断感。
- 对单个案例的观察，不自动升格为规律。先归为候选，再等待复用验证。
- 若用户明确给了组织特定规范，以用户规范优先，再与通用规律库对照。
- 若组织规范与通用规律冲突，不强行统一，必须明确标注冲突点与适用边界。

## 📖 案例实录 (Best Practice)

- 🧑‍💻 用户输入：
  ```text
  这周我们推进了 SKM+Hipo 招商沟通，团队分别对接了重点品牌和核心达人，目前已经拿到一批反馈，后续会继续跟进策略细化。
  ```
- 🤖 标准输出：
  ```text
  总评：这段话更像执行进度汇报，还不是决策型向上汇报。

  逐条打分：
  - 规律1：0/2 —— 开头没有先给出判断或管理含义。
  - 规律2：1/2 —— 提到了团队对接，但责任划分与资源覆盖仍不够清楚。
  - 规律3：0/2 —— 缺少时间点、反馈规模与目标锚点。
  - 规律4：1/2 —— 信息有并列项，但层次不够明显。
  - 规律5：0/2 —— 只有动作推进，没有诊断结论。

  总分：2/10

  改写建议：
  1. 先明确当前判断，例如“SKM+Hipo 招商已进入可规模化推进阶段”。
  2. 补充分工与资源覆盖，说明谁在负责品牌、谁在负责达人。
  3. 增加反馈规模、时间点和业务目标锚点。
  4. 先给诊断，再讲后续动作。

  改写后完整段落：
  当前判断是，SKM+Hipo 招商已从试探式沟通进入可规模化推进阶段：本周团队已分别完成重点品牌与核心达人两条线的首轮触达，并拿到首批有效反馈，说明供给侧对该方向有明确响应。下一步将基于反馈结果，优先细化招商策略与资源配置，确保后续推进从“持续跟进”升级为“按优先级拿结果”。
  ```
