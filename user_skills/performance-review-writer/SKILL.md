# Performance Review Writer

## Common Rationalizations（常见借口）

以下想法出现时，立即回到本 SOP：

- “素材不完整，先写一版漂亮话。”
- “先把做过的事情都列出来，再让用户自己挑重点。”
- “团队指标不错，就直接写成个人贡献。”
- “OKR 没给全，也可以凭项目名称猜目标。”
- “价值观映射只要贴标签，不需要具体行为和影响。”
- “向上汇报改写就是润色句子，不需要重构判断、分工和数字锚点。”

## Red Flags（危险信号）

出现任意一条，先纠偏再输出：

- 重点工作超过 5 条，且没有解释合并逻辑。
- 只写过程动作，没有结果、判断、动作、影响和协同方。
- 把团队大盘、市场自然增长或他人贡献直接归因给用户。
- 自评材料没有体现“合理预期 vs 实际产出”。
- 字节范或领导力原则只写抽象品质，没有对应事实。
- 输出像流水账、口号或过度包装，而不是可被上级校准的事实陈述。

## Verification（强制验收清单）

当宣称完成绩效写作时，必须同时满足：

1. **五步链路完整**：素材召回 → OKR 对齐 → 影响力量化 → 价值观映射 → 向上汇报改写均已执行。
2. **标准口径一致**：默认遵循 [绩效写作标准](references/performance-writing-standards.md)，尤其是“合理预期 vs 实际产出”和“重点工作不多于 5 项”。
3. **证据可追溯**：每条重点工作至少有素材来源、数据锚点或明确待补项。
4. **归因克制**：团队结果、市场结果和个人贡献被分开描述，个人贡献只写可验证动作与影响。
5. **结构可填写**：输出能拆成重点工作产出、自评、价值观举证、360 建议或向上汇报段落。
6. **向上汇报达标**：最终版本结论先行、分工清楚、数字有锚、结构分层、诊断语气可信。

## 📌 技能简介

本技能把绩效写作从“临时润色”变成一条可复用的材料加工链路。它先帮助召回与整理素材，再把素材对齐 OKR 和岗位合理预期，最后改写成上级容易校准、系统可直接填写的中文表达。

核心原则：少写事项，多写重点工作；少写努力，多写判断、结果和影响；少贴标签，多用事实证明做事方式。

## 标准参考

详细标准见 [绩效写作标准](references/performance-writing-standards.md)。执行复杂写作前先读取该文件，尤其是以下口径：

- 业务产出以“合理预期 vs 实际产出”为底层判断。
- 重点工作默认 2-5 条，优先保留能独立支撑校准的事项。
- 单条重点工作按“结果 → 背景/问题 → 关键动作 → 能力/影响”展开。
- OKR 对齐用于证明高优先级聚焦，不是把所有事情贴到目标下。
- 价值观举证必须写“行为 + 影响”，不写空泛品质。

## 五步 SOP

### Step 1. 素材召回

收集用户提供的 OKR、周报、项目复盘、看板指标、飞书文档、会议结论、360 反馈线索和旧版自评。若素材散乱，先按“候选重点工作”归组，而不是按来源平台平铺。

每条候选素材记录以下字段：

- **事项**：做了什么。
- **角色**：用户承担 owner、协同、执行、策略判断或机制搭建中的哪类责任。
- **结果**：可量化结果、阶段里程碑或组织影响。
- **来源**：文档、看板、会议或用户口述。
- **缺口**：缺数据、缺角色边界、缺影响说明或缺 OKR 对齐。

### Step 2. OKR 对齐

把候选事项映射到 2-4 个阶段核心目标。没有 OKR 原文时，用用户给出的工作目标或岗位职责做临时锚点，并显式标注“待用户确认”。

对齐时只保留能说明高优先级聚焦的事项。零散执行动作应合并到更大的重点工作中，除非它本身有清晰结果、复杂判断和独立影响。

### Step 3. 影响力量化

每条重点工作至少尝试补齐以下一种影响证据：

- **业务指标**：GMV、商家数、转化、效率、成功率、覆盖率、成本、周期等，必须带时间点和基线。
- **机制影响**：流程、标准、Playbook、看板、协同机制、团队分工等是否被复用。
- **组织影响**：推动哪些团队达成共识、争取哪些资源、降低哪些协作成本。
- **风险影响**：避免了什么损失、修正了什么偏差、提升了什么稳定性。

无法量化时，不编造数字；用“已确认事实 + 待补数据”表达。

### Step 4. 价值观映射

将重点工作映射到字节范或领导力原则时，使用“具体行为 → 当时约束 → 产生影响”的句式。避免写“我有主人翁精神”“我追求极致”这类抽象判断。

常见映射方向：

- **事实判断**：如何基于数据或一线反馈重新判断问题。
- **主动破局**：如何在资源不足、职责切换或跨团队复杂环境下推进。
- **坦诚清晰**：如何拉齐目标、暴露风险、推动取舍。
- **共同成长**：如何沉淀方法、带动团队或提升协作效率。
- **方向判断 / 做事风格 / 团队管理**：管理者或 owner 型职责可补充领导力原则。

### Step 5. 向上汇报改写

最终改写遵循五个检查点：

1. **判断先行**：开头先说这件事的业务含义或结论。
2. **分工清晰**：说明用户承担的角色、协同对象和资源覆盖。
3. **数字有锚**：数字带变化、时间点和目标背景。
4. **层次清楚**：优先用 2-4 个层次组织，不平铺十几条动作。
5. **诊断可信**：先说明问题本质和取舍，再说做了哪些动作。

## 合规默认值（Defaults）

- DEFAULT_LANGUAGE：简体中文。
- DEFAULT_OUTPUT_COUNT：重点工作 2-5 条，默认 3 条。
- DEFAULT_STRUCTURE：结果 → 背景/问题 → 关键动作 → 能力/影响。
- DEFAULT_EVIDENCE_MODE：无证据不编造，显式标注待补。
- DEFAULT_ATTRIBUTION_MODE：团队结果、市场结果、个人贡献分开描述。
- DEFAULT_REWRITE_MODE：按向上汇报五检查点重构，而不只做语言润色。

## 运行时断言

当输入将被用于正式文档、台账写入或跨工具传递时，先运行 `scripts/validate_payload.py <payload.json>` 校验结构。脚本会在缺失五步链路、重点工作超过 5 条、缺少角色/影响/证据状态时 `raise` 并熔断，避免把不完整素材写入后续系统。

## 输出模板

### 重点工作产出

```markdown
### [重点工作标题] — [周期]

**结果与影响：** [先写结果、变化和影响，带时间点/基线/范围]

**背景与判断：** [说明当时问题、合理预期、关键判断]

**关键动作：**
1. [动作一：用户角色 + 协同对象 + 动作]
2. [动作二：机制/策略/资源]
3. [动作三：验证与沉淀]

**价值观 / 领导力举证：** [具体行为 + 影响]

**待补材料：** [缺口，如无则删除]
```

### 自评段落

```markdown
本周期围绕 [核心目标]，重点推进 [重点工作]。在 [背景/约束] 下，先通过 [判断/方法] 明确优先级，再推动 [关键动作/协同机制] 落地，最终带来 [量化结果/组织影响]。这件事体现的主要贡献不是单点执行，而是 [owner 视角/机制搭建/跨团队协同/方向判断]。
```

### 360 评估人建议

```markdown
建议优先邀请能评价以下上下文的合作方：
- [业务方/区域/团队]：能评价目标判断与结果质量。
- [跨团队 owner]：能评价协同推进、资源整合和风险处理。
- [直接合作成员]：能评价日常做事方式、沟通透明度和方法沉淀。
```

## 质量边界

- 不替用户虚构结果、数据、职级或职责。
- 不把“努力、负责、积极”当作结论；必须落到事实。
- 不主动建议用户夸大档位或包装不可验证贡献。
- 若用户要求输出飞书文档或正式报告，使用 `lark-doc` skill 创建文档。

## ⚙️ 核心架构 / SOP / 约束条件

本技能采用“标准口径 + 写作链路 + 向上汇报校准”的结构。标准口径放在 reference 中，主 SOP 保持短链路，确保 Agent 在普通自评改写场景中可以直接执行；当涉及公司标准、职级合理预期、360 邀请或岗位职责切换时，先读取 reference 再写。

  ```
- 🤖 标准输出：

  ```
