# 前端预览稳定性原则

本文件提炼自《动态UI前端预览稳定性评估》中的高置信度结论，用于在生成或评审聊天内前端预览时快速对齐边界。

## 1. 总原则

- **稳定展示优先于运行时自由度。**
- **能编译时解决，就不要运行时解决。**
- **能使用 AUI 官方组件，就不要引入业务物料或第三方物料。**
- **展示型需求，用展示型方案解决。**

## 2. 稳定性分层

### 第一优先级：AUI 官方组件 + 快速预览
适用于：结构化展示、轻交互卡片、表单、小型配置面板、结果面板。

原因：
- 走编译时解析依赖，不依赖运行时临时拉包。
- 组件、样式、容器约束来自同一套官方基建。
- 可以规避大部分脚本拦截、外部依赖失败与样式错位问题。

### 第二优先级：AUI 轻交互卡片 / 展示型降级
适用于：单选、多选、状态展示、审核确认、简单筛选、标签编辑。

原因：
- 风险更小，开发更快。
- 用户心智稳定，不要求聊天容器运行完整前端工程。

### 第三优先级：静态展示 / 文档嵌入 / SVG / 受控 HTML
适用于：图表、流程说明、结果汇总、页面快照、可视化报告。

原因：
- 如果目标只是“稳定展示”，静态方案通常比动态运行更稳。
- 可以保留可读性，显著降低白屏概率。

### 第四优先级：受控 H5 预览
适用于：已存在成熟 H5 页面，需要复用页面而非重写卡片。

要求：
- 将其视作单独的“页面预览系统”问题处理。
- 需要接受 iframe、同域化、代理、登录态与 postMessage 的治理成本。
- 不要把它误当成聊天动态卡片的主链路。

### 默认不建议：第三方 React 运行时 + Sandpack 动态预览
原因：
- 需要依赖下载。
- 更容易命中 sandbox、iframe、CSP、跨域、登录态与插件干扰问题。
- 运行时异常会直接导致整棵 React 树卸载，体感即白屏。

## 3. 高风险黑名单

以下做法会显著提高白屏或拦截概率：

1. 将第三方 React 物料直接塞入动态预览容器。
2. 依赖外部脚本源或非白名单 CDN。
3. 在渲染主链路中直接读取环境变量、会话、JWT 或其他敏感上下文。
4. 在聊天容器中完整复用现成 H5 应用。
5. 依赖外部样式链路或让样式加载顺序决定成败。
6. 使用 inline script、`eval`、`new Function` 等动态执行方式。
7. 开启会改变 DOM 结构的浏览器插件、翻译插件或注入脚本扩展。

## 4. 强交互场景的三层兜底

如果需求必须进入强交互模式，至少补齐以下三层兜底：

### 运行时兜底
- 对关键参数做判空。
- 包裹异常边界（Error Boundary）。
- 提供明确空态与错误态提示。

### 数据兜底
- 接口失败时允许静态数据或空状态。
- 禁止因数据缺失导致整页崩溃。

### 产品兜底
- 提供“跳转完整版页面”“查看文档”“查看静态快照”的备用出口。
- 让失败路径仍然可用，而不是直接白屏。

## 5. 输出判断口诀

- **只想让用户看内容** → 静态展示 / 文档嵌入 / SVG / 受控 HTML。
- **只需要点几下完成任务** → AUI 官方组件 / 轻交互卡片。
- **需要中等交互** → 尽量仍留在 AUI 快速预览链路。
- **必须运行自定义前端工程** → 进入强交互治理模式，并显式给出风险与降级方案。
- **要复用完整网页** → 单列为 H5 预览问题，走受控 iframe / 同域代理方案。
