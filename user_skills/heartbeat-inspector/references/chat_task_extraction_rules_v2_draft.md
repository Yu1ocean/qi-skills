# 群聊任务提取与判定规则 v2.0（Draft）

> 适用场景：heartbeat-inspector 从飞书群聊增量消息中识别“需要录入的任务”，并输出结构化结果。
> 
> 本稿基于《【UK_EU_JP POP BD】群聊任务边界校准表》与用户负面反馈整理，作为后续 LLM Prompt / 规则引擎的核心草案。

---

## 1. 目标

从群聊消息中识别**需要录入的任务**，并保证：

1. **主题总结清晰**：总结必须稳定、结构化、可直接阅读。
2. **原文摘录完整**：必须 100% 保留原始群聊文本，不得省略、截断、改写。
3. **负责人提取完整**：不仅识别显式 @ 人，还要结合上下文还原泛指对象与完整责任映射。
4. **可用于后续自动化**：输出格式应适合后续 Diff、去重、入库、告警展示。

---

## 2. 基于校准表的边界结论

### 2.1 正样本共识
以下类型通常应判定为“是”：

1. **明确分派执行动作**
   - 例如：填写文档、跟进评论、整理 todo、制作方案。
2. **明确要求做出确认 / 判断 / 决策**
   - 即便是疑问句，只要本质上要求某人给出结论，也算任务。
3. **面向多人或泛指角色的协作任务**
   - 如“负责各自类目的同学填好”“大家看一下并准备明天定稿”。
4. **带有时间节点、会议节点、交付节点的行动要求**
   - 如“今早 11 点前确认”“明天开会前看完并定稿”。
5. **重复提及但本质仍是任务**
   - 需要识别为任务，但同时标记为“重复/并入已有任务”。

### 2.2 负样本共识
以下类型通常应判定为“否”：

1. **单纯时间确认 / 是否有空 / 行程沟通**
   - 例如“18:30 或 19:00 你方便吗”。
2. **泛泛的会议发言引导 / 讨论提纲**
   - 如果没有形成明确的执行动作、交付要求、负责人和结果物，不录入为任务。
3. **仅表达背景、同步信息、情绪或观点**
   - 没有动作要求、没有待办，不算任务。

### 2.3 本轮校准中暴露的关键问题

1. **主题总结不清晰**
   - 现有摘要容易写成松散口语，导致后续查看成本高。
2. **原文摘录不完整**
   - 出现省略号、截断和二次转述，失去溯源价值。
3. **负责人提取不完整**
   - 只抓单个 @ 或发送人不够，必须把上下文中的泛指责任人补齐。
4. **任务与重复任务未区分**
   - 像“是，与前一条重复”说明需要单独的重复判断字段。

## 3. 判定标准

### 3.1 判定为“任务”的必要条件
一条消息（或一组连续消息）满足以下任一条件，即可判为任务：

- 有明确的行动要求（做、填、跟进、整理、确认、输出、评审、制定、补充、推进、同步、回复等）。
- 有明确的交付物 / 事项对象（文档、评论、todo、方案、预算、标准、商家清单、汇报材料等）。
- 有明确的责任人或责任范围（显式 @ 人、群体角色、类目负责人、全体相关同学等）。
- 有明确的时间边界 / 节点（今天、今早 11 点、明天开会前、会上前、尽快等）。
- 虽然表面是疑问句，但本质是在推动某人作出确认、答复或决策。

### 3.2 判定为“非任务”的排除条件
若消息主要属于以下情况，则判为非任务：

- 单纯约时间、问是否有空、协调参会档期。
- 只是抛出讨论话题，没有形成明确动作。
- 只是同步背景信息，没有要求谁做什么。
- 只是情绪表达、提醒、寒暄、确认收到。

### 3.3 重复任务判定
若当前消息与最近上下文中的已识别任务在以下维度高度一致，则标记为重复任务：

- 核心动作一致；
- 交付物或事项对象一致；
- 负责人一致或是其子集；
- 时间节点一致或仅是对同一任务的补充提醒。

重复任务处理原则：

- `is_task = true`
- `is_duplicate = true`
- 保留当前消息的完整原文；
- 若能定位前序任务，则输出 `duplicate_of`。

---

## 3.4 【】锚点高优识别（强制）

当原始消息文本中出现被【】包裹的短语时：

1. **必须最高优判定该消息为任务**（`is_task = true`）。
2. **任务名称必须直接继承该【...】原话**（包含【】），不得改写/概括。
3. 若同一条消息中包含多个【...】短语，可输出多个任务（每个任务一个 `task_name`）。

若判定为任务但未出现【】锚点，则按第 4 节的兜底提炼规则生成任务名，并在输出时补齐【】。

## 3.5 高阶人机协同规则（v2.2）

### 3.5.1 【接单闭环追踪 (Ack-Lock)】

当识别出任务后，需要在后续消息中嗅探是否被责任人“认领”（例如回复“收到”“1”、点赞/OK 表情等）。

- 若未检测到认领：输出结构中标记 `[⚠️待接单/未响应]`。
- 若检测到认领：输出 `ack_lock.status = "acked"` 并记录证据。

### 3.5.2 【状态流转魔法词 (State-Triggers)】

如果针对某个任务的后续回复包含魔法词：

- `/done`（或 `/完成`）→ done
- `/阻塞` → blocked
- `/延期至xxx` / `/延期到xxx` → postponed

则需要输出 `status_update` 结构供后续看板状态同步。

### 3.5.3 【赛博时钟锚定 (Relative Time Anchoring)】

提取任务时，必须基于消息的绝对时间戳（create_time）将“下班前”“明早”等相对时间翻译为格式化的绝对时间：`YYYY-MM-DD HH:MM`。

- 若出现“尽快”“有空弄一下”等无法物理锚定的时态：必须触发逆向提醒（suggestion_reply），提示补充明确 DDL，并建议使用【任务名称】格式。

## 4. 主题总结范式（强制）

所有任务摘要必须使用以下结构：

**[动词] + [交付物/事项] + [时间节点/约束（如有）]**

要求：

1. 必须以动作开头，禁止空泛名词化表达。
2. 必须点明对象，不可只写“跟进一下”“看一下”。
3. 若原文存在明确时间节点，必须写入摘要。
4. 若原文存在明确合作关系，可在摘要中保留“与谁共同”。
5. 摘要应简洁但信息完整，避免口语、避免堆砌背景。
6. **符号强制**：最终任务名必须包裹在【】内，例如：`【确认是否纳入抖音商家及招募标准（今早11点前）】`。

### 4.1 推荐动词表

填写、跟进、确认、整理、制定、补充、评审、准备、汇总、输出、同步、回复、推进、对齐、审阅、定稿。

### 4.2 示例

- 好：`填写各自类目文档内容`
- 好：`确认是否纳入抖音商家及招募标准（今早11点前）`
- 好：`整理文档 todo 与团队诉求`
- 好：`与王臻阳共同制定 Y2 模式商家方案`
- 差：`这个事情跟进下`
- 差：`关于商家的问题`
- 差：`大家看看文档`

## 5. 原文摘录规则（强制 100% 完整保留）

### 5.1 必须保留的内容
输出中必须保留群聊消息的**完整原文**，包括但不限于：

- 全部文字内容；
- 全部换行；
- 全部 @ 人；
- 全部链接、文档名、引用标记；
- 全部标点、语气词、括号补充；
- 多条连续消息时的原始顺序。

### 5.2 明确禁止

- 禁止使用 `...` / `…` 省略；
- 禁止为了摘要美观而删改原文；
- 禁止去掉换行并压平成一句；
- 禁止只保留片段；
- 禁止把原文替换成“整理后版本”。

### 5.3 输出要求

需要至少区分两个字段：

- `summary`：结构化任务摘要
- `source_text_full`：完整原文，逐字保留

如果任务来自多条连续消息，应输出：

- `source_messages_full`: 按时间顺序保存完整消息数组

---

## 6. 负责人提取规则（强制完整）

### 6.1 责任人识别优先级
按以下顺序提取责任人：

1. **显式被 @ 的人**
2. **消息中直接点名的人**
3. **发送人给自己/本方团队布置的任务**
4. **上下文中已经定义过的泛指角色**
   - 如“各自类目的同学”“负责 HIPO 的同学”“大家”
5. **协作对象**
   - 如“和@王臻阳一起做”应识别为共同负责人

### 6.2 泛指映射要求
当原文出现泛指对象时，不能只输出模糊称谓，必须尽量结合上下文补全映射。

例如：

- `负责各自类目的同学` → 应尽量映射成具体名单 + 各自职责
- `大家` → 应结合当前群范围或上下文限定，说明是“全体群成员”还是“相关项目成员”
- `你们几个` → 应追溯上文确定具体是谁

若上下文足以还原，应输出：

- `owners`: 具体责任人列表
- `owner_mapping`: 责任人到职责范围的映射

若上下文仍不足，也不能假装确定，应输出：

- `owners_inferred_group`: 泛指对象原文
- `owner_resolution_status = "partial"`
- `owner_resolution_evidence`: 用于推断的上下文依据

### 6.3 发送人与负责人不能混为一谈

- 发送人不必然是负责人；
- 如果发送人是在给别人派活，负责人应是被指派人；
- 如果发送人说“我来补”“我去确认”，则发送人本人是负责人；
- 若为协同任务，可同时保留 `assigner` 与 `owners`。

## 8. 供 LLM 直接使用的 Prompt 核心草案

你是一个“群聊任务提取器”。

你的任务是：从给定的群聊消息及其上下文中，识别是否存在“需要录入的任务”，并输出结构化结果。

### 判定原则

1. 只要消息中存在明确的动作要求、交付物/事项对象、责任人、时间节点中的任意关键组合，即可判定为任务。
2. 即使表面是疑问句，只要本质是在推动某人确认、答复、做决定，也要判定为任务。
3. 单纯约时间、问是否有空、参会协调、背景同步、情绪表达，不判为任务。
4. 如果当前消息与前文已识别任务本质相同，应判为任务，但标记为重复。

### 输出要求

1. 必须先判断 `is_task`。
2. 若为任务，必须输出：
   - `summary`
   - `owners`
   - `owner_mapping`（能还原时必须给出）
   - `due_time`（有则必填）
   - `deliverable`
   - `source_text_full`
   - `evidence`
3. `summary` 必须严格采用：**[动词] + [交付物/事项] + [时间节点/约束（如有）]**。
4. `source_text_full` 必须逐字保留原文，严禁使用省略号、严禁截断、严禁改写。
5. 负责人提取必须完整：
   - 不仅提取显式 @ 人；
   - 还要结合上下文还原泛指对象；
   - 若无法完全还原，也要输出部分推断结果和证据，不可假装确定。
6. 发送人和负责人分开识别，不得混淆。
7. 如果是多人协同任务，`owners` 必须列出所有负责人，而不是只保留第一个名字。

### 摘要质量要求

- 好的摘要必须让人脱离上下文也知道要做什么。
- 禁止写成“跟进一下”“看一下”“这个事情处理下”。
- 若有明确时间节点，必须体现在摘要中。
- 若任务涉及共同完成，可保留“与某人共同”。

### 原文保真要求

- 保留所有换行、@人、链接、标点。
- 不允许使用 `...` 或 `…`。
- 不允许把多条消息压缩成一句话。
- 如果任务来自多条消息，按时间顺序完整输出每条消息。

## 9. 对 heartbeat-inspector 的落地建议

结合当前实现，建议下一步至少做这几项改造：

1. **停用 `_safe_excerpt()` 的截断逻辑**
   - 现实现会压平空白并截断到 140 字，不满足 v2.0 要求。
2. **在 `run_inspector.py` 的 `new_msgs` 处理环节引入 LLM 提取层**
   - 不再直接把原消息拼成告警文案，而是先做“任务识别 + 结构化提取”。
3. **支持“上下文窗口”输入**
   - 不能只看单条消息，至少要支持同一时段相邻消息联合判定。
4. **增加重复任务字段**
   - 支持 `is_duplicate` / `duplicate_of`。
5. **告警文案与结构化产物分层**
   - 告警文案给人看；结构化 JSON 给后续存储、去重、回查使用。

---

## 10. 建议的最小验收标准

若升级完成，至少应满足：

1. 正样本中所有“是”都能识别为任务；
2. 明确为“否”的时间协调类消息不再误判；
3. 摘要统一符合 `[动词] + [交付物/事项] + [时间节点]`；
4. 原文字段中不再出现任何省略号式截断；
5. 多负责人场景下，不再只提取一个人；
6. 对“是，但与前一条重复”能打出重复标记。
